# 貼文整理、結構化抽取與場次瀏覽需求

本文件描述目前功能需求；操作方法見[操作指南](../development/post-etl-operations.md)，網站互動見[使用指南](../user-guide.md)。程式驗證與人工語意驗收分開，不以測試通過宣稱全量抽取正確。

## 1. 目標與實作限制

在既有 Facebook 擴充功能、本機 SQLite 歷史庫、羽球整理 scripts 與頁面原型上，補齊可續跑、可追溯的整理流程。使用者匯入抓取結果後，同一篇貼文以最新擷取版本為準，本文轉為結構化場次，並可在簡單頁面中自行搜尋、排序及篩選。

本需求採原地演進：

- 沿用現有 Node.js、SQLite、JSON Schema、CLI 與測試工具。
- 既有模組具備相近責任時，直接擴充；不得另建一套 ETL、歷史庫、抽取器或查詢引擎。
- 僅對目前缺少的持久化任務管理、流程協調及正式場次頁面新增必要模組；名稱與檔案拆分由實作依現有結構決定。
- 不以搬移既有 scripts、改框架、改 repo 結構為前置工作。
- 不修改爬蟲擷取方式、Chrome 權限、Facebook 資料來源或既有 raw 匯出格式。
- 不新增雲端後端、多使用者系統、自動排程、多 agent 流程或圖片辨識。
- 結構化範圍為球友揪團、場地租借／轉讓、教練課程與正式賽事，不辨識運動項目。

## 2. 模組責任

| 功能 | 位置 | 責任 |
| --- | --- | --- |
| 擷取與匯出 | src/ | 頁面資料擷取、批次去重與原始 JSON／CSV |
| 貼文歷史 | scripts/post-archive/ | 原始觀察、識別鍵、最新資料與歷史查詢 |
| 準備抽取 | skill 的 scripts/prepare.mjs | 來源保存、穩定 ID、網址遮罩與 context |
| 任務協調 | scripts/task-store.mjs、scripts/etl.mjs、scripts/codex-extract.mjs | 任務狀態、模型呼叫、有限重試、版本及發布紀錄 |
| 規則與驗證 | references/、scripts/lib/validation.mjs | 分類與玩法契約、缺值、欄位一致性 |
| 合併與發布 | scripts/join.mjs、scripts/finalize.mjs | ID 關聯、服務分流、JSON／CSV 及一致發布 |
| 網站 | scripts/browser.mjs、scripts/browser-runtime.mjs | 單一 HTML、桌面表格與手機卡片 |
| 查詢與檢查 | scripts/query.mjs、scripts/validate.mjs、tests/ | 條件查詢、跨產物一致性與品質評估 |

除 src/ 與歷史庫之外，以上相對位置皆位於 skills/badminton-session-finder/。沿用這些模組，不另建替代 ETL 或平行網站實作。

## 3. 處理流程

```text
既有爬蟲匯出 JSON
  → 匯入既有 SQLite，保存原始觀察
  → 按貼文識別鍵選最新擷取觀察
  → prepare：建立或重用抽取任務
  → LLM：依固定任務契約產生 analysis
  → join／validation：逐篇驗證並記錄結果
  → finalize：發布該篇最新合格結果，產生 JSON／CSV／報告
  → 頁面：讀取完整已發布集合，搜尋、排序、篩選與查看原文
```

既有獨立 CLI 命令繼續可用，作為檢查與重跑入口。新增協調入口負責串接步驟，不複製步驟內的邏輯。LLM 結果仍可透過既有 JSONL 交接；本需求不以新增模型供應商 SDK 或自動 API 呼叫為完成前提。

## 4. 功能需求

### R1. 貼文識別、原始觀察與最新版本

- 沿用 archive 的 `post_key`：正規貼文網址優先、社團範圍的貼文 ID 次之、內容指紋後援。
- 相同正規網址必須歸同一 key；沿用目前網址正規化，不要求發出網路請求解析所有 Facebook 網址別名。
- 缺乏可靠識別時保留識別種類與品質警告。內容指紋不得宣稱能可靠串起修改前後的貼文，也不得自動用模糊相似度合併來源。
- 每次有效新觀察追加保存，保留 raw、批次、來源及時間；最新查閱透過選擇觀察完成，不覆寫 raw 歷史。
- 有合法 `scraped_at` 的觀察以該時間由新到舊選取；相同時以 `written_at`、`observation_id` 決定穩定順序。
- 缺少或無效擷取時間的觀察不得擠掉已有合法擷取時間的觀察；全部皆無合法擷取時間時，才依寫入時間選取，並標示時間品質問題。
- 同一份標準 raw JSON 重複匯入時，不新增相同邏輯觀察或抽取任務；只回報已匯入。既有重複歷史不在本次清除範圍。
- 檔案內容改變時仍可形成新觀察；「重複檔案」與「同篇新觀察」必須分開判斷。
- 最新觀察若截斷仍保留其最新身分並標示品質；不得靜默拼接不同觀察的本文當作新 raw。

[ADR 0004](../adr/0004-archive-exports-in-local-sqlite.md)、`CONTEXT.md`、README 與相關測試皆以最新合法擷取時間定義 latest；後續調整須同步維護。

### R2. 來源關聯與抽取重用

- 區分貼文識別鍵、來源觀察 ID、抽取任務 ID 與場次 ID；不得把目前含批次與陣列位置的抽取 `id` 當成跨批次貼文 key。
- 保留現有 `{id, context}` → `{id, analysis}` 交接形式與按 ID join。新增來源關聯保存在程式擁有的來源／任務紀錄，模型不產生 key、觀察 ID 或來源 metadata。
- 抽取重用依據必須涵蓋：同一貼文的有效輸入 context、抽取規則版本、schema 版本與模型設定版本。
- context hash 必須包含實際影響抽取的時間、時區與截斷資訊；不能只比本文而錯用日期分析。只有互動數改變、有效 context 不變時才可重用。
- 若相同 analysis 被重用到新觀察，輸出的來源 metadata、聯絡網址及原文必須依新觀察重新組裝與驗證，不沿用舊的整份 listing。
- context 或抽取契約版本改變後，建立待處理任務；成功的相同任務不重複分析。提供針對指定貼文或失敗任務的明確重跑入口。

### R3. 每次 LLM 抽取都有完整任務契約

- 擴充既有 skill 和 extraction references，明確描述「區分球友揪團、場租／轉讓、教練課程與正式賽事，拆出獨立項目，不辨識運動項目」；不讓模型自行決定要摘要、搜尋或編寫 ETL。
- 每次處理必須取得同版目的、規則、schema 與範例，不只提供裸 context。JSONL 交接時亦須可辨識此次使用的契約版本。
- context 沿用本文、參考時間、時區、截斷標示；需要發布時間作為證據時，只提供 raw 中可靠的值，另保留擷取時間與參考時間來源，禁止混稱為發布時間。
- 「今天／明天」不能無條件以擷取日換算；缺少可信時間錨點時保留不確定。月日缺年份沿用現有參考時間與星期規則，衝突時不得強填。
- 貼文文字只作為來源資料，其中的指令不能修改抽取規則。
- 保留既有網址 inventory、遮罩與程式組裝方式；模型不得生成網址。
- 不屬上述四類的貼文輸出 `is_recruitment=false` 與空 listings；資訊不足的招生貼文保留分類、缺值與警告，不為了產生場次而補造資料。
- 範例至少涵蓋：單場次、多日期／多時段配對、固定週期與明確日期、跨午夜、條件價格、缺值／截斷、非招生、來源衝突。
- 同篇多時段不得做笛卡兒積；同場次的條件價格維持既有 `price_options[]`。
- schema 使用 end_day_offset 表達跨日，避免只存 `00:00` 而丟失日期關係。

### R4. 驗證與品質分類

- 所有結果通過既有 schema、未知／重複 ID、原文證據及聯絡值驗證後才可發布；逐篇路徑和既有 join／validate 使用同一套規則。
- 新模型輸出只保留結構化資訊，不要求重複原文、evidence、title、notes 或 confidence；讀取已有 evidence 的結果時，仍檢查已填事實的引用與覆蓋，不允許用空 evidence 規避驗證。
- 證據欄位路徑須對應實際已填資料，quote 須逐字存在於送入模型的本文。缺值不要求虛構證據。
- 驗證實際存在的日曆日期、時間與跨日關係、數值合理性、範圍上下界及分類與 listings 的一致性。
- warning 使用固定代碼集合，另以訊息說明個案，不以任意自然語言充當代碼。需定義「阻止發布」與「可發布但需確認」的分類。
- 格式錯誤、未知來源、捏造 quote 等拒絕發布；原文明確缺價、缺地點或截斷等可保存為缺值與品質提示。
- 證據逐字命中不代表推論正確，語意準確度另以人工標註樣本驗收。模型自評 confidence 不作為唯一發布依據。
- 既有歷史結果若不符新契約，回報需重驗／重抽；不得放寬驗證或自動補證據。

### R5. 逐篇狀態、續跑與報告

- 持久化任務管理使用既有本機 SQLite，不引入另一套儲存系統。
- 每篇可辨識待處理、處理中、成功、失敗；成功結果另有是否需人工確認的品質資訊，發布狀態另行記錄。
- 保存來源觀察、context hash、契約／模型設定版本、嘗試次數、開始／完成時間及可定位的錯誤原因。人工 JSONL 交接亦需保存此次模型設定紀錄。
- 中斷後可恢復待處理及未完成工作，不重跑已成功任務；殘留處理中狀態可經明確恢復操作重新排入，避免永久卡住。
- 一篇失敗不應阻止其他已驗證貼文完成，但整批須明確標為部分完成，列出失敗與未完成 ID。既有 join 預設缺 ID 即報錯的嚴格行為繼續保留。
- 自動重試如有啟用，必須有次數上限；修正模型結果時提供具體驗證錯誤，不靜默丟棄欄位。手動重試亦不得覆蓋已發布成功結果。
- 沿用 `run_report.json`，新增待處理、成功、失敗、重用、需確認、已發布及舊版暫留數量，並說明統計單位。來源貼文數與場次數不可混算。

### R6. 結構化結果一致發布

- 沿用 finalize 與 JSON／CSV 輸出契約，以來源 key 和觀察關聯判斷發布版本。
- 同一篇新結果通過驗證後，整組替換其已發布場次；新版刪除的場次不得殘留。
- 新版確認為非招生，或有效結果已沒有可發布場次時，撤下該篇舊場次。
- 新版抽取失敗或尚未完成時，可暫留上一個成功結果，但必須標示「來源已有新版，整理尚未更新」，並保留新舊觀察關聯；不得當作最新整理完成。
- 舊任務較晚完成時，不得覆蓋目前較新觀察的成功發布結果；發布前重新檢查目標觀察。
- 同一篇版本更新不拆成逐場次半套寫入。JSON／CSV／報告與頁面資料須屬同一發布批次；中斷時仍可讀上一批完整產物，不讀混合版本。
- 跨貼文場次去重沿用 `lib/dedupe.mjs` 的獨立責任，與來源版本選擇分開。不同貼文疑似同場不自動刪除 raw 或來源關聯。

### R7. 場次瀏覽與選取

- 單一 HTML 含完整已發布主場次集合與該批 CSV；其他三種服務輸出獨立 JSON／CSV，暫無專屬網頁。
- 預設不分組，每列顯示日期與時間；切換日期分組不因排序而切回。各模式保留獨立的三段排序（升序、降序、取消）。日期排序週期置頂、明確日期其次、未知最後，未知欄位值置後。
- 搜尋涵蓋原文、地區、場館與程度；篩選包含玩法、新手友善、費用上限、最早開始時間、日期、星期及日期星期交集方式。已套用條件可個別取消。
- 不提供獨立地區、場館、程度文字或招募狀態選單。網站包含已滿與取消，確定重複預設隱藏。
- 顯示日期、時間、場館、玩法、程度、時數、費用、每小時費用與來源入口。聯絡與原文不排序；完整價格條件與原文可展開。
- 點整列選取，來源連結、作者操作與詳情不誤觸選取。底部預覽與複製包含原文及兩種來源網址，上限 50 場及 100,000 個 Unicode 字元，超限不截斷。
- 作者名稱可開啟過濾選單，可靠識別對應的排除條件可取消；選取與過濾不持久保存。
- 手機以左標籤右數值卡片呈現，上方沿用可換行的表頭排序按鈕；上下導航避開底部選取工具列。

### R8. 服務分類與玩法

- 每筆新增 listing_type（session、venue_rental、coaching、tournament）、單一可空玩法與對應 service_details。混合貼文按獨立服務拆列，共用來源，不重複摘要原文。
- 玩法包括雙打、男雙、女雙、混雙、單打、男單、女單。不限搭配用雙打；明確男女搭配才用混雙；未說明留空，不按慣例補值。
- 場租、課程與賽事保留各自計費單位、安排、條件及截止等專屬欄位，使用同一流程及原子發布。不同服務類型不合併去重。
- 舊分析不自動補分類；發布補空值並保留原 ID，既有未分類資料仍留在主表。規格與欄位以[抽取 schema](../../skills/badminton-session-finder/references/extraction.schema.json)及[輸出契約](../../skills/badminton-session-finder/references/output-contract.md)為準。

## 5. 相容性與既有資料

- 既有 raw 匯出、archive import/latest/history 及 badminton prepare/join/finalize/query/validate 入口繼續可用；需要新增選項時同步更新 help。
- 新流程以擴充既有入口或新增協調命令承接，不建立並存的替代實作。
- SQLite 結構若擴充，須有明確 schema 升級方式；保存既有 raw 和觀察 ID，不要求清空資料庫重建。
- 抽取 schema、任務與輸出需可識別版本；保留 `{id, context}` 和 `{id, analysis}` 頂層形狀，版本可由程式側執行紀錄關聯。
- 舊 JSONL／結果不保證通過較嚴格的新契約，但必須給出可操作的重驗或重抽訊息，不可不明原因失敗或默默混入新發布。
- `output/` 中現有個人資料與原型產物不是待清理對象，不覆寫既有檔案來完成遷移驗收。
- 模型交接支援人工 JSONL 與已登入的 Codex CLI；模型設定保存在專案設定檔，不將憑證寫入任務資料。

## 6. 驗收條件

| 編號 | 情境 | 必須觀察到的結果 |
| --- | --- | --- |
| A1 | 相同網址的新舊批次以相反順序匯入 | 同 key、raw 歷史保留，最新查閱與 ETL 都選較新擷取觀察 |
| A2 | 重複匯入同一 raw 檔，並再次執行整理 | 不新增相同邏輯觀察，不重跑已成功相同任務，不重複發布場次 |
| A3 | 部分觀察缺擷取時間，或只有指紋識別 | 不錯誤擠掉可靠最新觀察，顯示時間／識別品質資訊 |
| A4 | context 或契約版本更新；僅互動 metadata 更新 | 前者排入抽取；後者在有效 context 相同時可重用，但輸出來源更新 |
| A5 | 結果亂序、未知／重複 ID、既有 evidence 覆蓋不足、虛構 quote、非法日期、未知 warning | 按 ID 正確合併亂序結果，其餘依契約拒絕並指出欄位與任務 |
| A6 | 同篇多時段、週期、跨日、條件價格及缺值 | 配對不交叉，跨日不丟失，價格條件保留，不憑空補值 |
| A7 | 執行到一半中斷，一篇結果無效 | 恢復後只處理未完成／指定失敗任務；有效貼文可發布，批次顯示部分完成 |
| A8 | 新版由三場改為一場，再改為非招生 | 依序只剩一場、零場；歷史 raw 與舊分析仍可追溯 |
| A9 | 新觀察抽取失敗，或舊任務晚於新任務完成 | 舊成功結果如暫留則標示未更新；過時任務不覆蓋新版發布 |
| A10 | 產物發布中斷 | 頁面仍讀同一批完整結果，JSON／CSV／報告不混版 |
| A11 | 頁面清除全部條件，再套用相同 CLI 條件 | 可查完整已發布集合；相同條件、重複／狀態設定產生相同 listing ID 集合 |
| A12 | 缺價、免費、條件價、未知程度、原文含 HTML | 缺價不當零元，條件可見，未知不當友善，文字不執行 |
| A13 | 既有資料庫與舊結果升級 | raw 與歷史可讀，舊結果明確通過或要求重驗／重抽，CLI 仍可用 |

抽取品質另建至少 30 篇去識別化、人工確認的真實貼文樣本，涵蓋 R3 列出的各類案例。標註應包含預期場次数、日期／時間／場地配對、價格條件、關鍵缺值與可接受歧義，不能只檢查 schema 通過。

固定樣本驗收須無捏造關鍵事實、無錯配場次，且符合標註的可接受答案或不確定表達；另報告漏抽場次與各關鍵欄位正確率。未達者記錄失敗案例並修正抽取契約後重驗，不宣稱全量資料已正確。

## 7. 完成定義

每次變更通過對應的 archive、抽取／分流／查詢及頁面測試，必要時執行 npm run check。發布驗證須涵蓋主表與三組服務表，另檢查玩法群組篩選、三段排序、手機對齊與選取複製限制。

可由原始 JSON 完成可追溯抽取與一致發布，失敗可定位續跑，既有資料與 CLI 保持相容。人工語意樣本與真實頁面驗收分別報告，不以單元測試代替。
